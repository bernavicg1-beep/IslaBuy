Reading the before/after panels

The top bar is the interface — what callers must know. The block below is the implementation. A shallow module is a wide bar over a thin block: callers carry the complexity instead. A deep module is a narrow bar over a tall block: the complexity lives behind the seam. The deletion test applies to every candidate — would deleting it concentrate complexity, or merely move it?

Candidate 1

A Listing mapping module

Strong

data/repository/ListingRepository.kt · data/model/Listing.kt

Problem

The same query→model shape repeats five times: documents.mapNotNull { it.toObject(Listing::class.java)?.copy(id = it.id) }. The "is this listing live?" predicate is applied in the repository and again in HomeViewModel.loadProducts(). Collection names are bare strings in four files. Change "active means status==active and not expired" and you edit five call sites.

Solution

One module owns the collection name, the snapshot→Listing conversion, and the active/expired predicate. Callers ask for live listings for a category; they no longer know that Firestore documents need their id patched in, or that expiry is a client-side filter.

Before — shallow, replicated

map + filter + collection name ×5
5 lines of real logic, copied

After — deep, single seam

liveListings(category?, cursor?)
query build · mapping · expiry policy · pagination

Benefits

Locality: the expiry rule has one home, so it can't drift between feed and category views. Leverage: a new screen pays one call, not six lines. Tests: the mapping and predicate become testable without a Firestore emulator — today the only tested expiry code is in ProductFilter, which production never calls.

Candidate 2

One authority for "who is in this conversation"

Strong

ChatRepository.kt:50 · ConversationListViewModel.kt:27 · firestore.rules

Problem

Membership is encoded three incompatible ways: getConversationsForUser() queries whereArrayContains("participants", …) — a field the Conversation model does not have and nothing ever writes; ConversationListViewModel queries buyerId == userId only, so sellers see an empty inbox; and firestore.rules says buyer or seller. Three answers, one question.

Solution

A conversation-access module exposes belongsTo(userId), keyFor(product, buyer, seller) and canDeleteForEveryone(message, userId). The repository, both view models and the rules derive from it. The dead participants query and the duplicated key builder in MessageValidator collapse into it.

Why this first

This is not only a structure problem — it is a live defect. A seller cannot see any of their conversations today. Deepening this module fixes a broken acceptance criterion while it removes the duplication.

Candidate 3

Give expiry a clock, not a locale

Strong

data/model/Listing.kt:28-38 · util/ProductFilter.kt

Problem

isExpired() parses two strings with a SimpleDateFormat("yyyy-MM-dd HH:mm") built on Locale.getDefault(), compares against Date(), and swallows every exception into false — so a malformed date silently means "never expires". It is also called inside filter {} loops, re-parsing per comparison, with no seam to inject "now" in a test.

Solution

Move the rule behind ExpiryPolicy.expiresAt(listing): Instant? with an injected clock. The model keeps a thin isActive(clock). Parsing happens once, malformed data becomes an explicit "unknown" the UI can surface, and every caller shares one definition of expired.

Before

isExpired() · isActive() · clock = wall time
3-line parse, locale- and second-dependent

After

isActive(clock)
parse once · Locale-safe · explicit unknown · shared by feed, category, seller

Benefits

Testing becomes trivial — a fixed clock makes expiry assertions deterministic instead of time-of-day dependent. Locality: the "unknown date" case stops being a silent false hidden in a catch.

Candidate 4

Account deletion as its own module

Worth exploring

data/repository/UserRepository.kt:29-52 · docs/account-deletion.html

Problem

A profile repository owns a cross-collection cascade — it reaches past ListingRepository into listings and stores with raw string collection names, deletes the user doc, then deletes the auth account last. Any failure mid-way leaves a half-deleted account that the UI reports as an error with no state. The published policy page promises conversations and messages are deleted too; the code never touches them. Code path and promise have drifted apart.

Solution

An AccountDeletion module states the deletion graph in one place — what is removed, in what order, what is retained — and returns a resumable outcome. UserRepository goes back to profiles. The policy page and the tests both read from the same declaration.

Before — divergent change

UserRepository: profile CRUD and cascade delete
listings · stores · users · auth

After — one reason to change each

UserRepository
profiles
AccountDeletion
graph + order

Candidate 5

Delete the test-only utility layer — or make it the seam

Worth exploring

util/ProductFilter.kt · util/MessageValidator.kt · util/ListingValidator.kt

Problem

Three objects whose interface is as wide as their implementation — seven one-line filter {} wrappers, six boolean predicates. Nothing in ui/ or data/ calls them; only the unit tests do. So the green test suite proves a layer that ships in the APK and does no work, while the paths users actually hit — repositories, view models — are untested.

Solution

Either delete them and inline into the one place each rule applies, or invert the dependency: make the repository and view models call the validators. The second keeps the tests and makes the tested seam the production seam. The interface narrows to predicates; the depth comes from being enforced at the boundary rather than duplicated beside it.

Deletion test

Deleting ProductFilter concentrates nothing — its logic is already restated in ListingRepository. Deleting ListingValidator would lose a rule that SellScreen may not enforce, so it should be kept and wired, not removed. Two different verdicts from the same test — which is the point of applying it.

Candidate 6

Notification preferences that reach the notification

Speculative

data/preferences/NotificationPreferences.kt · notifications/IslaBuyMessagingService.kt · IslaBuyApp.kt

Problem

Four DataStore keys with getters and setters and no reader: nothing in the messaging service consults messageSoundsEnabled before posting, and no channel sets a sound at all. The module has a complete interface and an empty effect — callers pay the import, users get nothing.

Solution

If per-type muting is wanted, the preference belongs behind the notification presenter: one module decides "should this message notify, and how loud", and the service asks it. Otherwise remove the module until something reads it.

Why speculative: the right fix depends on whether configurable ringtones are still in scope. Deciding that is a product call, not an architectural one — so this is last.

Top recommendation

Start with Candidate 2 — one authority for conversation membership

It is the only candidate that pays twice. Structurally it retires three competing encodings of one rule — a query on a field that does not exist, a buyer-only filter, and a rules clause — and gives the chat feature a single seam to test through. Practically it fixes a seller who currently opens an empty Messages screen, which no amount of further feature work will reveal because every test passes.

Follow it with Candidate 1: once the conversation module shows the shape of a good seam, the listing mapping module follows the same pattern and removes five copies of the same three lines. Candidates 3–6 are cheaper afterwards, because 1 and 2 establish where such logic is supposed to live.
